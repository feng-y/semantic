P0：先解决“能不能持续跑”的问题

目标不是做大而全，而是让 semantic harness 从“可演示”变成“可持续使用”。

P0-1 增量发现

这是第一优先级。

你文档里已经明确指出，全量扫描是核心成本问题，尤其在大型项目下，时间和 token 消耗都会成为瓶颈。增量发现是最直接的收益项。 ￼

目标

把 discover 从“每次扫全库”改成“默认扫变更”。

最小落地形态
    •   支持 --incremental
    •   基于 git diff 找变更文件
    •   只重跑受影响模块
    •   未变化部分直接复用现有 fact/baseline

验收标准
    •   首次全量正常
    •   二次增量耗时显著下降
    •   增量输出和全量输出结构兼容
    •   变更范围外内容不被误重写

⸻

P0-2 智能分级审查

这是第二优先级。

你的文档里把人工审查列为第一瓶颈，这个判断是对的。真正要做的不是“取消人工审查”，而是把人工只留给高风险部分。 ￼

目标

把 review 从“全量人工确认”改成“按置信度分级处理”。

最小落地形态
    •   高置信度：自动接受并记录日志
    •   中置信度：异步待审
    •   低置信度：阻塞审查

最小命令能力
    •   semantic-discover --auto-accept high
    •   semantic-review --priority high

验收标准
    •   审查对象数量显著下降
    •   高风险项仍然能被明确卡住
    •   自动接受项都有可追溯日志
    •   review 输出能区分 auto / manual / pending

⸻

P0-3 结构化验证

这是我建议补到 P0 里的第三项。

你文档里把“缺乏验证机制”列为核心问题，但我建议先做结构验证，不要一开始就上“LLM 语义验证”。 ￼

目标

先验证“生成的东西是不是结构上自洽”。

最小落地形态
    •   模块是否存在
    •   依赖是否真实
    •   路径是否有效
    •   baseline / semantic 输出是否符合 schema
    •   review 决策是否只含 allowed actions

最小命令能力
    •   semantic-validate

验收标准
    •   发现 schema drift
    •   发现引用不存在
    •   发现输出缺字段
    •   能阻止明显错误基线进入后续阶段

⸻

P0-4 semantic-status 的下一步建议

这是一个小投入高收益项。

你的文档里“智能建议”部分很好，但现在不需要一步到位做很复杂，只要先把 semantic-status --next 做出来就够。 ￼

目标

让用户不用自己判断下一步执行什么。

最小落地形态
    •   识别当前状态
    •   给出下一步命令
    •   解释为什么是这一步
    •   标出阻塞原因

验收标准
    •   用户在中断后能快速恢复流程
    •   review / finalize 等卡点能被明确提示
    •   推荐命令和实际状态一致

⸻

P1：再解决“好不好用”和“会不会越来越好”的问题

P1 不是平台化，而是让这套系统开始进入“可迭代优化”。

P1-1 反馈循环

你文档里把它列为最关键三项之一，我同意，但我会放到 P1。 ￼

目标

从 agent / 用户实际使用里学到：
    •   哪些知识有用
    •   哪些知识没被用
    •   哪些地方出错最多

最小落地形态
    •   记录查询命中
    •   记录失败点
    •   记录 fallback 场景
    •   输出改进建议报告

最小命令能力
    •   semantic-feedback --from agent-logs

验收标准
    •   能看出最常被用的知识块
    •   能定位最容易错的字段/模块
    •   能形成下一轮 discover / review 优化建议

⸻

P1-2 缓存层

这个很重要，而且比插件化、分布式更应该先做。

你文档里对 cache 的判断是对的：这是性能和成本的直接收益点。 ￼

目标

避免重复分析不变内容。

最小落地形态
    •   文件级 hash
    •   AST cache
    •   fact extraction cache
    •   analysis cache

验收标准
    •   未变化文件不重复分析
    •   依赖变化可触发级联更新
    •   cache 不会污染 baseline 正确性

⸻

P1-3 集成现有工具

这个值得做，但建议分层做，不要一次做满。

你文档里提到 LSP、静态分析、文档导入，我建议顺序是：
    1.  LSP
    2.  文档导入
    3.  linter / type checker

目标

减少重复工作，提高结构信息准确性。 ￼

最小落地形态
    •   semantic-discover --use-lsp
    •   semantic-import --from docs/adr/
    •   后面再考虑 --integrate-linters

验收标准
    •   符号/引用提取更准
    •   现有 ADR/OpenAPI 能成为初始基线输入
    •   人工重复录入显著减少

⸻

P1-4 多格式导出

这个不是不重要，但比验证和反馈稍后。

目标

让 semantic/fact 产物更容易被其他系统消费。 ￼

最小落地形态
    •   JSON 导出
    •   Markdown 导出保持
    •   暂不急着做 GraphQL

验收标准
    •   JSON 能直接给其他 agent / tool 消费
    •   Markdown 仍适合人工审查
    •   导出格式和内部 schema 一致

⸻

我不建议现在进入 P0/P1 的内容

这些方向不是错，而是现在做会稀释主线。

先别做
    •   分布式处理
    •   GraphQL API
    •   交互式 shell
    •   全面插件化
    •   大规模可视化平台
    •   单 skill 上的 --auto 串全流程

这些更适合在主链稳定后进入 P2。

⸻

最终执行顺序

P0
    1.  增量发现
    2.  智能分级审查
    3.  结构化验证
    4.  semantic-status --next

P1
    1.  反馈循环
    2.  缓存层
    3.  LSP / 文档集成
    4.  JSON 多格式导出

一句话版本

如果你现在只能做最关键的四件事，那就是：

增量发现、分级审查、结构验证、状态推荐。

这四个做完，semantic harness 才会从“能跑一次”变成“团队愿意持续用”。 ￼
