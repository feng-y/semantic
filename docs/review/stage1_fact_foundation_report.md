# Stage 1 — FACT Foundation Report

## 1. Facts Artifacts Overview

This stage stabilizes the **FACT layer** of the semantic pipeline. FACT artifacts are the
primary products of the discovery & review phases and the inputs to refinement/baseline.

FACT artifacts:

1. **repo-facts**
   - Purpose: structured inventory of repository technologies, modules, entrypoints,
     core entities, and configuration.
   - Generated by: `prompts/discover/repo-facts.prompt` (discovery step 1).
   - Location: `docs/semantic/discovery/repo-facts.vN.md`.

2. **domain-candidates**
   - Purpose: candidate domain groupings inferred from repo-facts (early domain model).
   - Generated by: `prompts/discover/domain-candidates.prompt` (discovery step 4).
   - Location: `docs/semantic/discovery/domain-candidates.vN.md`.

3. **repo-understanding**
   - Purpose: high-level understanding of system purpose, pipelines, concepts,
     and candidate domains.
   - Generated by: `prompts/discover/repo-understanding.prompt` (discovery step 5).
   - Location: `docs/semantic/discovery/repo-understanding.vN.md`.

4. **knowledge-confidence**
   - Purpose: explicit separation of confirmed / inferred / uncertain knowledge
     about the system.
   - Generated by: `prompts/discover/knowledge-confidence.prompt` (discovery step 7).
   - Location: `docs/semantic/discovery/knowledge-confidence.vN.md`.

5. **review-summary**
   - Purpose: human-readable summary of the system for architect review
     (pipelines, concepts, domains, assumptions, questions).
   - Generated by: `prompts/discover/review-summary.prompt` (discovery step 8).
   - Location: `docs/semantic/review/review-summary.vN.md`.

All FACT artifacts are written via `src/artifact_writer.py` and versioned under
`docs/semantic/discovery/` or `docs/semantic/review/`.

## 3. Validation Rules

FACT artifact validation is implemented in `src/artifact_validation.py`.

For each artifact, the validator:
- rejects empty content; and
- checks that the content contains **at least one** expected section heading,
  using `_has_any_section_heading(content, SECTIONS)` with a case-insensitive
  `## Heading` pattern.

Validators:

1. `validate_repo_facts(content: str) -> list[str]`
   - Uses `REPO_FACTS_SECTIONS = ("Repository", "Modules", "Entrypoints", "Core Entities", "Configuration")`.
   - Errors:
     - `"repo-facts: artifact content is empty"` when content is empty.
     - `"repo-facts: missing required schema sections ..."` when **none** of the
       expected headings is present.

2. `validate_repo_understanding(content: str) -> list[str]`
   - Uses `REPO_UNDERSTANDING_SECTIONS = ("System Purpose", "Pipelines", "Concepts", "Candidate Domains")`.

3. `validate_knowledge_confidence(content: str) -> list[str]`
   - Uses `KNOWLEDGE_CONFIDENCE_SECTIONS = ("Confirmed Knowledge", "Inferred Knowledge", "Uncertain Knowledge")`.

4. `validate_domain_candidates(content: str) -> list[str]`
   - Uses `DOMAIN_CANDIDATES_SECTIONS = ("Candidate Domains",)`.

5. `validate_review_summary(content: str) -> list[str]`
   - Uses `REVIEW_SUMMARY_SECTIONS = ("System Summary", "Pipelines", "Concepts", "Candidate Domains", "Assumptions", "Questions for Architect")`.

**Known limitation (not changed in Stage 1):**
- Current FACT validation uses a **"has any"** strategy (at least one section heading
  present), not a strict **"all required sections must be present"** strategy.
- This is sufficient for catching fully malformed artifacts (no schema sections), but
  does not enforce complete coverage of all schema sections.

## 5. Facts Already Stable vs Fixes vs Remaining Gaps

### 5.1 Facts already stable (before Stage 1)

These aspects of the FACT layer were already in place and remain unchanged:

- Discovery pipeline order and behavior (`src/discovery_executor.py`):
  - repo-facts → domain-candidates → repo-understanding → knowledge-confidence → review-summary.
- Artifact writing, versioning, and snapshot logic (`src/artifact_writer.py`).
- Core validation functions and section lists in `src/artifact_validation.py`.
- System-level tests that exercise discovery, refinement, baseline, and failure
  handling (`tests/test_system.py`, `tests/test_step7_hardening.py`,
  `tests/test_step8_verification.py`, etc.).

### 5.2 Fixes applied in Stage 1

1. **Added missing schema for domain-candidates**
   - File: `docs/semantic/schemas/domain-candidates.schema.md`.
   - Defines Candidate Domains section with fields: Domain Name, Description,
     Related Pipelines.

2. **Introduced FACT templates**
   - Directory: `docs/semantic/templates/`.
   - Files:
     - `repo-facts.template.md`
     - `repo-understanding.template.md`
     - `knowledge-confidence.template.md`
     - `domain-candidates.template.md`
     - `review-summary.template.md`
   - Templates align with existing schemas and current artifact shape, and follow
     the heading/list style used by `fake_executors.stub_executor`.

3. **Added Stage 1 FACT foundation tests**
   - File: `tests/test_stage1_fact_foundation.py`.
   - Encodes the FACT-level acceptance criteria for this stage.

4. **Validated full test suite after changes**
   - `pytest -v` now runs 229 tests, all passing.

### 5.3 Remaining gaps (deferred to later hardening)

These items are explicitly out of scope for Stage 1 and will be addressed in
later IBS / hardening stages:

1. **Stronger structural validation for FACT artifacts**
   - Future work: move from "has any section" to "all required sections present"
     or richer section-level rules that fully leverage schema definitions.

2. **Tighter schema/runtime alignment**
   - Some schema fields (e.g., Evidence, Confidence, Assumptions) are not enforced
     by validators today.

3. **IBS integration and new artifacts**
   - Stage 1 intentionally does **not** introduce any IBS artifacts, prompts, or
     baseline changes; those will build on this stabilized FACT foundation.

4. **State/reporting enhancements**
   - `state_inspector` and status-related APIs were not modified in Stage 1.
