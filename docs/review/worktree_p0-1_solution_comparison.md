# 方案对比分析：修复实现 vs 更新测试

**问题**: worktree-p0-1-incremental-signals 有 44 个测试失败
**核心问题**: 实现和测试不匹配

---

## 📊 方案对比表

| 维度 | 方案 A: 修复实现 | 方案 B: 更新测试 |
|------|------------------|------------------|
| **时间成本** | ✅ 1小时 | ❌ 4小时 |
| **代码质量** | ❌ 倒退到旧设计 | ✅ 保留更好的设计 |
| **API 设计** | ❌ 通用但不必要 | ✅ 专注且合理 |
| **长期维护** | ❌ 保留不够好的设计 | ✅ 更易维护 |
| **测试覆盖** | ✅ 测试不变 | ⚠️ 需要重写测试 |
| **风险** | ✅ 低风险 | ⚠️ 可能引入新问题 |

---

## 🔍 详细分析

### 方案 A: 修复实现以匹配测试

#### 优点 ✅
1. **快速** - 只需 1 小时
2. **低风险** - 测试已经存在，不会引入新问题
3. **简单** - 只改实现代码，不动测试
4. **测试契约** - 遵循"测试定义 API"的原则

#### 缺点 ❌
1. **设计倒退** - 回到不够好的旧设计
2. **通用性过度** - `ChangeDetector` 不需要那么通用
3. **数据结构不合理** - `merge_signals` 用列表而不是分类字典
4. **长期债务** - 保留了不够好的设计

#### 具体影响

**ChangeDetector 倒退**:
```python
# 方案 A: 通用但不必要
ChangeDetector(state_file, patterns=["*.yaml", "*.py"])
# 调用者需要知道跟踪什么文件模式

# 当前设计: 专注且简单
ChangeDetector(fact_root, cache_dir)
# 内部知道跟踪 fact_canonical_sample.yaml 等
```

**merge_signals 倒退**:
```python
# 方案 A: 简单但不合理
merged = cache.merge_signals([sig1, sig2], [sig3])
# 返回: [sig1, sig2, sig3]
# 问题: 不区分信号类型

# 当前设计: 复杂但合理
merged = cache.merge_signals(cached_dict, new_dict)
# 返回: {
#   'domain_signals': [...],
#   'concept_signals': [...],
#   ...
# }
# 优点: 按类别组织
```

---

### 方案 B: 更新测试以匹配实现

#### 优点 ✅
1. **保留更好的设计** - 新 API 更合理
2. **专注性** - `ChangeDetector` 专门为 FACT → Semantic 设计
3. **数据结构合理** - 信号按类别组织
4. **长期收益** - 更好的设计更易维护
5. **正确的方向** - 设计演进应该更新测试

#### 缺点 ❌
1. **时间成本高** - 需要 4 小时
2. **工作量大** - 需要重写 44 个测试
3. **风险** - 可能在重写测试时引入新问题
4. **需要理解新设计** - 测试需要正确反映新行为

#### 具体影响

**测试需要大幅修改**:
- 18 个 `test_change_detector.py` 测试
- 2 个统计测试
- 7 个 merge_signals 测试
- 10 个 incremental_extraction 测试
- 7 个其他相关测试

## 🎯 深度对比

### 1. API 设计质量

**ChangeDetector API**:

| 方案 A (旧) | 方案 B (新) | 评价 |
|-------------|-------------|------|
| `(state_file, patterns)` | `(fact_root, cache_dir)` | **新更好** |
| 通用，可跟踪任意文件 | 专门为 FACT 设计 | 专注 > 通用 |
| 调用者指定模式 | 内部硬编码 | 简化调用 |
| 灵活但复杂 | 简单但专注 | 简单获胜 |

**merge_signals API**:

| 方案 A (旧) | 方案 B (新) | 评价 |
|-------------|-------------|------|
| `(List, List) -> List` | `(*Dict) -> Dict` | **新更好** |
| 简单列表合并 | 分类字典合并 | 结构化 > 扁平 |
| 不区分类型 | 按类别组织 | 类别化更合理 |
| 调用者管理分类 | 内部管理分类 | 封装更好 |

**结论**: 新 API 设计明显更好 ✅

---

### 2. 代码质量

**方案 A**:
- ❌ 保留不够好的设计
- ❌ 技术债务累积
- ✅ 代码改动小

**方案 B**:
- ✅ 保留更好的设计
- ✅ 减少技术债务
- ❌ 测试改动大

**结论**: 方案 B 代码质量更高 ✅

---

### 3. 长期维护性

**方案 A**:
```python
# 每次调用都需要指定模式
detector = ChangeDetector(state_file, ["*.yaml", "*.py"])
# 如果要改跟踪的文件，需要改所有调用处

# 信号合并不区分类型
merged = cache.merge_signals(cached, new)
# 调用者需要自己管理 domain/concept/rule 分类
```

**方案 B**:
```python
# 调用简单，内部管理
detector = ChangeDetector(fact_root, cache_dir)
# 如果要改跟踪的文件，只改一处

# 信号自动按类别合并
merged = cache.merge_signals(cached_dict, new_dict)
# 内部处理分类，调用者不用管
```

**结论**: 方案 B 更易维护 ✅

**方案 A 风险**:
- ✅ 低实现风险（只改代码）
- ❌ 高设计风险（保留不好的设计）
- ❌ 长期债务风险

**方案 B 风险**:
- ⚠️ 中等实现风险（重写测试可能出错）
- ✅ 低设计风险（保留好的设计）
- ✅ 无长期债务

**结论**: 方案 B 总体风险更低 ✅

## 🎯 推荐理由

### 1. 新设计明显更好
- **专注性**: 专门为 FACT → Semantic 设计，不需要通用性
- **合理性**: 信号按类别组织，符合实际数据结构
- **简洁性**: 调用者不需要知道内部细节

### 2. 长期收益大于短期成本
- **短期**: 多花 3 小时（4h vs 1h）
- **长期**: 更好的设计，更易维护，减少技术债务
- **ROI**: 值得投入

### 3. 这是正确的开发流程
- 设计演进 → 更新测试
- 不是倒退到旧设计
- 测试应该反映当前设计

### 4. 避免技术债务
- 方案 A 会累积技术债务
- 未来可能还要重构
- 不如现在一次做对
