**Date:** 2026-03-21
**Status:** Draft — pending team architecture confirmation

## Overview

Two-phase commit analysis system using Claude Code native **Team Agent** architecture:
- **commit-extract**: Main agent orchestrates workers that regenerate commit logs from diffs, grouped by month
- **commit-semantic**: Main agent orchestrates workers for split→analyze→aggregate→distill

---

## Critical Constraints

### 1. Commit Log Must Be Regenerated from Diff

**COMMIT LOG IS NEVER TAKEN FROM ORIGINAL COMMIT MESSAGE OR ISSUE TEXT.**

The commit log must be **regenerated by Claude Code** based on the actual code diff. Original commit message is stored as `original_message` (reference only). The canonical field is `commit_log`.

### 2. Team Agent Architecture (NOT Python + executor)

Skills run inside Claude Code's native team mode:

```
User triggers /commit-extract or /commit-semantic
    ↓
SKILL.md expands into current context (main agent)
    ↓
Main agent orchestrates via TeamCreate / TaskCreate / Task / SendMessage
    ↓
Worker agents do the actual LLM analysis (isolated context, no main context bloat)
    ↓
Workers return results to main
    ↓
Main agent writes YAML files
```

**Key principle:** Skill is an instruction template, not a Python script that calls `executor()`. The main agent is the scheduler, workers are the analysts.

## commit-extract

### Purpose

Collect git commits, regenerate commit logs from diffs using Claude Code team workers, group by month.

### Input
- Git commits (CC-generated, multi-day, multi-purpose collections)

### Output
```yaml
# data/commit-extract/2024-03.yaml
metadata:
  month: "2024-03"
  total_commits: 45

commits:
  - commit_id: "abc123"
    timestamp: "2024-03-15T10:30:00"
    author: "yan."
    original_message: |  # Original git message (reference only)
      feat: add parser legacy support
    files: [...]
    diff_chunks: [...]
    commit_log: "在 parser 中补充 legacy 语法的边界检查处理"  # REGENERATED from diff
```

### Stages
1. **collect**: Worker agents analyze diffs and regenerate commit logs, main agent groups by month

### Output Fields
| Field | Source | Purpose |
|-------|--------|---------|
| `commit_id` | git | Identifier |
| `timestamp` | git | Temporal grouping |
| `author` | git | Attribution |
| `original_message` | git commit message | Reference only |
| `files` | git diff-tree | Change scope |
| `diff_chunks` | git show | Raw diff for LLM analysis |
| `commit_log` | **Claude Code (worker agent)** | Regenerated from diff |

### Worker Batch Strategy

Commits are batched (e.g., 20-50 per worker) to avoid token bloat:
- Main agent prepares batches from git
- Each worker receives one batch with full diff context
- Worker regenerates commit_log for each commit in batch
- Worker returns structured results (YAML/JSON)
- Main agent aggregates and writes monthly YAML files

## commit-semantic

### Purpose

Cross-commit semantic analysis, scoring, canonical demand extraction via team agents.

### Input
- data/commit-extract/*.yaml (reads `commit_log` field, NOT original_message)

### Output
```
data/commit-semantic/
├── units/all.yaml              # Split by module
├── functional/
│   ├── high/units.yaml         # Score >= 8
│   ├── medium/units.yaml       # Score 5-7
│   └── low/units.yaml          # Score < 5
├── non-functional/
│   └── all/units.yaml
└── patterns/
    └── {module}.yaml
```

### Classification

| Prefix | Category | Scored |
|--------|----------|--------|
| `feat:` | functional | Yes |
| `bugfix:` | functional | Yes |
| `optimize:` | functional | Yes |
| `refactor:` | non-functional | No |
| `refactor+bugfix:` | functional | Yes (semantic priority) |
| `test:` | non-functional | No |
| `config:` | non-functional | No |
| `cleanup:` | non-functional | No |

### Stages
1. **split**: Parse commits by module (reads `commit_log` from extract output)
2. **analyze**: Workers score functional commits (clarity, domain, reusability)
3. **aggregate**: Group by module, extract patterns
4. **distill**: Extract canonical demands from high-scored

### Scoring Criteria (Functional Only)
- Clarity: Is commit_log clear and specific?
- Domain: Is module/domain identified?
- Reusability: Can this pattern be reused?

## Team Architecture Detail

### commit-extract Team Structure

```
Team: "commit-extract"
Main: (current agent, scheduler)
  - Reads git commits
  - Splits into batches (by month or by N commits)
  - Creates tasks for workers
  - Collects results from workers
  - Writes data/commit-extract/YYYY-MM.yaml

Workers: N x "commit-log-generator"
  - Receives: batch of commits with diff_chunks
  - Task: For each commit, regenerate commit_log from diff
  - Returns: List of {commit_id, commit_log}
  - Context: Isolated, no access to other commits
```

### commit-semantic Team Structure

```
Team: "commit-semantic"
Main: (current agent, scheduler)
  - Loads data/commit-extract/*.yaml
  - Orchestrates: split → analyze → aggregate → distill
  - Writes output files

Workers: N x "commit-analyzer"
  - Receives: batch of units (commit_log + metadata)
  - Task: classify, score, extract patterns
  - Returns: Structured results
```

## Key Decisions

1. **Team Agent Architecture** — Main as scheduler, workers as analysts. Not Python + executor().
2. **COMMIT LOG IS REGENERATED FROM DIFF** — Worker agents analyze diffs and produce commit_log.
3. **Batch Processing** — Commits batched (20-50 per worker) to control token usage.
4. **commit_semantic reads commit_log** — Not original_message. This is the canonical field.
5. **Original message preserved** — Stored as `original_message` for reference only.
6. **Incremental Support** — Workers skip already-processed commits (tracked by main agent).
